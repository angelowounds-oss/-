# NEON CITY V9 — 비판적 총평 (2026-10-09)

> 2026-10-10 갱신: 제품 방향이 **자유 샌드박스**로 결정되었다(`docs/design/core-loop.md`). 아래 GPL 평가의 "핵심 루프 불명확"은 "행동 폭 × 도시 반응 폭"을 키우는 과제로 바뀐다.

대상: `neon-city-v9` 브랜치 `ebe2e86` 시점 전체. 근거는 이 저장소의 코드·커밋 이력(188개)과 `tests/` 회귀 스위트, 그리고 이번 세션의
측정값(SwiftShader 헤드리스 Chromium)이다. **실제 GPU 기기에서 측정한 수치는 하나도 없다** — 이 문서의 모든 성능 판단은 그 한계를 전제로 한다.

## 0. 한 줄 요약

**기술 데모로서는 범위가 넓고 엔지니어링 밀도가 높지만, "게임"으로서의 핵심 루프·콘텐츠 깊이·출시 준비(테스트 자동화, 빌드 배포, 저장
호환, 라이선스)는 아직 프로토타입 단계다.** 지난 몇 라운드의 작업은 기능 추가와 성능 미세조정에 집중되어 있었고, 그 결과 "시스템은 많고
각각은 동작하지만, 플레이어가 반복해서 할 일이 무엇인지"가 흐리다. 다음 단계의 우선순위는 기능 추가가 아니라 **기반(테스트·CI·배포·실기기
측정)과 핵심 루프**다.

## 1. 평가 기준

- **성숙도**: L1 프로토타입 · L2 동작함(데모 가능) · L3 안정(회귀 테스트로 보호, 알려진 큰 결함 없음) · L4 완성도(콘텐츠/폴리시 충분) · L5 출시 가능
- **상태 태그**
  - **[정체]** 이 환경·현재 구조에서 추가 투자 대비 효과가 낮다. 더 나아가려면 전제(측정 수단, 구조 변경, 외부 자원)가 먼저 바뀌어야 한다.
  - **[개선 여지]** 무엇을 하면 좋아지는지가 분명하고 지금 착수할 수 있다.
  - **[취약]** 결함·리스크가 있어 우선 착수가 필요하다.

## 3. 파트별 상세

### 1) 렌더링 — L3 [정체]
**잘 된 것**
- 프러스텀 컬링(실내 층·가구·유리·스키닝 메시), 원경 인스턴스 패킹, 조명 루프 생략, 컬러그레이드 패스 병합: 모두 **픽셀 동일성을 자동 테스트로 증명**(`cull-identity`, `pack-identity`, `light-skip-identity`). 거리 장면 삼각형 약 111만 → 85~93만.
- 플레이 중 셰이더 컴파일 0회(`no-runtime-compile`), 표지판 텍스처 배열의 컨텍스트 복구(`sign-ctx-restore`).
- 파사드 셰이더 반점(보간 오차) 제거, 출입구 구멍 제거 같은 시각 결함 수정 이력이 좋다.

**비판**
- **GPU 측정이 0이다.** 모든 GPU 최적화의 효과는 SwiftShader의 CPU 래스터 시간과 삼각형 수로 추정했다. SwiftShader는 장면이 커지면 JIT 캐시 스래싱으로 프레임당 1~2초 멈추기 때문에 GPU 타이밍 측정 자체가 이 환경에서 불가능하다 → **[정체]의 직접 원인**.
- 그림자: 2048 PCF-soft 한 장으로 ±85 m를 매 프레임 갱신(약 8 cm/텍셀). 캐스케이드·캐싱이 없다. 그림자 패스가 GL 호출의 약 17%.
- 후처리 체인(블룸 + SMAA + 출력)은 고정. 모바일 저사양용 경량 경로(블룸 축소, SMAA→FXAA)는 없다.
- 거리 LOD가 메시 단위로 없다(건물 원경은 인스턴스·스카이라인으로 처리, 차량·사람은 가시성 토글 위주).

**더 가려면**: PERF-01 실기기 GPU 타이머(EXT_disjoint_timer_query) 오버레이 → 그 데이터로 그림자/후처리 결정.

### 2) 성능·안정성 — L2~L3 [취약]
**잘 된 것**
- "총을 쏘면 프레임이 계속 낮아짐"의 원인(경로 탐색 평균 540 ms, 최대 6.1초)을 찾아 평균 0.6 ms로 해결.
- 층 생성 최장 단계 45 ms → 8 ms 미만, 물리 보간(120/144 Hz 끊김 제거), 동적 해상도의 60 Hz 복귀 버그 수정, 층 버퍼 풀링(이동 중 신규 버퍼 메모리 약 −74%).

**비판**
- **메이저 GC 정지 10~40 ms가 걷기 25초에 약 10회.** 원인은 JS 힙의 중수명 객체 승격(프레임당 약 89 KB)과 three.js 내부 WeakMap·Blink 객체 추적. 현재 구조(매 프레임 객체 생성, three.js 의존)에서는 **[정체]** — 구조 변경(객체 풀/ECS형 데이터) 없이는 더 줄지 않는다.
- **로딩**: 29.3 MB 단일 HTML(에셋 17.9 MB를 base64로 내장 → 약 1.33배 + 디코딩 메모리 2배). 실기기 로딩 시간 미측정.
- **안정성**: `main.js`의 `fatal()`이 업데이트 중 예외 하나로 게임 루프를 영구 정지시킨다. 오류 보고·복구·텔레메트리 없음.
- 성능 회귀를 막는 기준선은 이번에 처음 만들었다(`docs/PERF-BASELINE.md`, `frame-time`/`gunfire-load`/`nav-perf` 테스트). 실기기 기준선은 없다.

### 3) 월드·건물 — L2~L3 [개선 여지]
**잘 된 것**: 불규칙 그리드 도시, 보행자 거리, 지하철 입구, 약 300동 입장·층 스트리밍(생성기 3 ms 예산), 엘리베이터, 벽 파괴, 구역별 정전, 외곽 지형·호수·항만, 거주 동 66개의 실제 모델 외피.
**비판**
- 실내가 절차 생성이라 층·동 사이의 반복감이 크다(같은 가구 세트, 같은 방 배치 규칙). "AAA 밀도" 계획(표면·트림·욕실·주방)은 반영됐지만 **동선 설계·랜드마크 공간**(로비 외 특별한 장소)이 부족하다.
- `building.js` 78 KB에 계획(plan)·지오메트리 생성·가구 배치·문/엘리베이터 런타임·상호작용이 함께 있다. 회귀 테스트는 생겼지만 수정 비용이 크다.
- 층 스트리밍은 플레이어 기준 ±2~3층. 고층 창밖 조망, 다른 건물 내부의 원경 표현은 없다.

### 4) 물리·차량 — L3 [정체]
**잘 된 것**: Rapier 강체 + 레이캐스트 서스펜션, 차체 변형, 오토바이·보트·헬기, 12조각 랙돌(관절 제한, 일어나기), 고정 60 Hz + 렌더 보간(`physics-interp`), 차 지붕 타기·뛰어내리기.
**비판**
- 캐릭터 컨트롤러가 차량과 충돌하지 않아 OBB 밀어내기와 "가상 지붕"으로 우회했다. 경계 상황(경사, 고속)의 일관성은 검증이 얕다.
- 핸들링·충돌 손맛은 사람의 플레이 피드백 없이는 판단 불가 → **[정체]**(기술 부채가 아니라 검증 수단 부재).

### 5) 캐릭터·애니메이션 — L2 [개선 여지]
**잘 된 것**: UAL 클립 리타깃, 장총 2본 IK(펌프·볼트·탄창), 권총 상체 클립, 거리 LOD(75 m 밖 스키닝 생략).
**비판**: 모든 인물이 한 메시(Soldier) + 색 변경. 체형·얼굴·헤어·의상 실루엣 다양성이 없어 군중이 복제처럼 보인다. 표정·립싱크 없음. 이동 블렌딩은 Idle/Walk/Run 3종이라 방향 전환·정지 시 발 미끄러짐이 있을 수 있다(미측정).

### 6) AI·사회 시스템 — L2~L3 [개선 여지]
**잘 된 것**: 시야 원뿔·기억·소리 조사·수색·엄폐/엿보기·측면 우회·후퇴, 시민 공포 전파·웅크림·구경, 경찰 무전 수색, 5성 군 투입(헬기·탱크), 주민 2,000명의 일과(버스·지하철·엘리베이터), 목격 기반 신고, 뉴스·소문.
**비판**
- 전투 AI가 `ai.js combat()`의 상태 분기 + 매직 넘버로 쌓였다. 행동 트리/유틸리티 AI 같은 구조가 없어 새 행동을 넣을수록 상호작용 버그 위험이 커진다.
- 경로 탐색은 이제 빠르지만 매 호출 격자를 새로 래스터화한다(층별 캐시 없음). 실외 장거리 경로·차량 경로는 단순 규칙.
- 난이도·밸런스 데이터가 코드에 흩어져 있다(조정하려면 코드 수정).

### 7) 게임플레이·콘텐츠 — L1~L2 [취약]
**잘 된 것**: 시스템의 폭(무기 5종+근접+수류탄, 부착물, 상점·ATM·전당포·집 구매, 일자리, 인벤토리, 휴대폰, 수배, 이동 장비, 샌드박스).
**비판(가장 중요)**
- **핵심 루프가 정의되어 있지 않다.** 미션은 짧은 의뢰 7개 내외, 목표·보상·성장이 서로 연결되지 않는다. "왜 계속 플레이하는가"에 대한 답(서사, 영역 장악, 수집, 경제 목표 등)이 없다.
- 10월 7일 커밋의 일부("WIP, tests pending": 부착물, 차량 탈출/지붕 타기, 샌드박스)는 이후 정식 검증 기록이 없다.
- 경제·난이도 밸런스 데이터와 플레이 테스트가 없다.
- 기능 추가 속도가 폴리시 속도를 계속 앞질렀다(라운드마다 새 시스템). 이 흐름을 끊고 루프 하나를 완성도 있게 만드는 것이 다음 마일스톤의 핵심이다.

### 8) UX/UI·입력 — L2 [개선 여지]
**잘 된 것**: HUD, 미니맵, 휴대폰(지도·주민·뉴스·연락처·일자리·은행·카메라), 도움말(K), 터치 버튼·게임패드, 설정 저장, FPS 오버레이의 느린 프레임 원인 표시.
**비판**: 첫 플레이 온보딩이 없다(조작이 매우 많음). 문자열이 한국어로 코드에 하드코딩(다국어 불가). 키 재설정·색약 모드·자막 크기 등 접근성 없음. 모바일은 터치 레이아웃만 있고 실기기 성능·조작 검증이 없다. 이번 최적화로 게임 중 HUD 패널의 배경 블러를 제거(시각 변경, 의도된 트레이드오프).

### 9) 오디오 — L2 [정체]
**잘 된 것**: 에셋 0 바이트로 무기별 발사음·재장전 단계·표면별 발소리·실내 머플링·음악 진행·위치 기반 시민 목소리·뉴스 TTS·더킹. 노드 누적 위험 제거(공유 패너, 체인 해제).
**비판**: 합성음의 품질 상한(실제 녹음 대비 "칩튠" 느낌), 공간화는 스테레오 패닝뿐(HRTF/거리 감쇠 모델 없음), 라우드니스 기준 없음. 더 가려면 **"녹음 샘플을 번들에 넣을 것인가"라는 제품 결정**이 먼저 필요하다 → [정체].

### 10) 저장·데이터 — L1~L2 [취약]
- 저장 = `localStorage` JSON(`{cash, mission, kills, world: state}`), **스키마 버전 필드 없음**, 구버전 호환은 플래그(`gear1` 등)로 산발 처리.
- 저장 실패는 `catch { /* ignore */ }`로 조용히 무시 → 용량 초과 시 진행이 사라져도 알 수 없다.
- 탄흔 700개·이벤트 200개·주민 사망 기록 등 누적 데이터의 크기 예산이 없다.

### 11) 아키텍처·코드 품질 — L2 [개선 여지]
- `Game`(game.js 119 KB, 약 1,770줄)이 입력·플레이어·차량·사람·경찰·미션·HUD·렌더 순서를 모두 가진 갓 오브젝트. 51개 모듈이 `G.*`로 서로 직접 접근한다.
- 프레임 내 실행 순서(플레이어 → 차량/물리 → 사람 → … → 카메라 → HUD → 렌더)에 정확성이 의존한다(예: 렌더 보간, 지붕 타기 표시). 이번에 `docs/ARCHITECTURE.md`로 문서화했지만 코드로 강제되지는 않는다.
- 한 줄에 여러 문장을 압축한 스타일. 주석 품질은 좋지만 diff 리뷰 비용이 크다. 린트·포맷터·타입 검사가 없다.
- 테스트가 `window.__game` 내부 구조에 직접 의존한다 → 리팩터링 시 테스트도 함께 바뀌어야 한다(테스트 전용 API 계층 필요).

### 12) 빌드·QA·릴리스 — L1→L2 [취약]
- **이번 라운드 이전에는 회귀 테스트가 모두 임시 폴더에 있었다**(컨테이너가 사라지면 소실). 이번에 `tests/`로 옮기고 합격 기준을 붙였다(18개, `node tests/run.cjs`, 전체 18/18 통과). **CI는 아직 없다.**
- 29.3 MB 빌드 산출물을 140번 커밋 → `.git` 1.8 GB. 클론·푸시 비용이 계속 커진다(GitHub 단일 파일 100 MB 한도는 아직 아래).
- `build/`에 임시 스크립트(`t.mjs`, `tt.mjs`, `*_tmp.mjs`, `char_t2..t7.mjs`)가 섞여 있다. `package.json`에 스크립트가 없다.
- **라이선스 리스크**: 물 셰이더가 GPL-2.0-or-later 코드의 포팅이며 단일 번들에 다른 코드와 함께 배포된다 → 번들 전체의 배포 조건에 영향. CC-BY(Ferrari) 표기는 README에만 있고 게임 내 크레딧이 없다. "프로젝트 소유자 제공" 자산의 라이선스 근거가 문서화되어 있지 않다.

## 4. 정체 vs 개선 여지 요약

| 구분 | 영역 | 이유 / 풀리는 조건 |
|---|---|---|
| **정체** | 렌더링 GPU 최적화 | GPU 계측 수단 없음 → PERF-01(실기기 GPU 타이머) 후 재개 |
| **정체** | 메이저 GC | three.js·프레임 객체 생성 구조 → ARC 데이터 구조 개선 후 재개 |
| **정체** | 물리 손맛, 오디오 품질 | 사람 플레이 피드백 / 녹음 에셋 도입 결정 필요 |
| **개선 여지** | 월드 내부 다양성, 캐릭터 다양성, AI 구조, UX 온보딩, 아키텍처 분리 | 착수 가능, 범위 명확 |
| **취약(우선)** | 게임플레이 루프, 저장 버전, 빌드·CI·배포·라이선스, 예외 처리 | 제품·운영 리스크 |

## 5. 권고 우선순위
1. **M0 기반**: CI에서 `tests/run.cjs quick` 자동 실행, 빌드 산출물 커밋 중단(릴리스 아티팩트로 배포), 저장 스키마 버전, 예외 복구, 라이선스 정리.
2. **M1 실측**: 실기기 성능 오버레이(GPU 시간, 프레임 분해, 로딩 시간)와 기준선 → 렌더링/성능 결정을 데이터로.
3. **M2 핵심 루프**: 진행 구조 하나(예: 구역 장악 또는 범죄 경력 사다리)를 끝까지 완성, 미션을 데이터로 정의.
4. **M3 폴리시**: 캐릭터 다양성, 온보딩, 오디오 결정, 실내 랜드마크.
