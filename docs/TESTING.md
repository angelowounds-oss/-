# 테스트

`tests/run.cjs`가 실행하는 회귀 스위트. 모든 브라우저 테스트는 헤드리스 Chromium(SwiftShader WebGL2)으로 빌드된 게임 폴더(`dist/Korea/game`)를
`tests/lib.cjs`의 `serve()`(127.0.0.1 임의 포트, Range 206, 런처와 같은 MIME)로 열고 `window.__game`을 직접 조작한다(ADR-0034). 전략과 한계는 [ADR-0007](adr/0007-test-strategy-swiftshader.md).

## 메모리 (2026-11-02)
- 이 컨테이너의 셸 프로세스는 합쳐서 14.3 GB(cgroup)를 넘으면 강제 종료된다. 브라우저 렌더러가 죽으면 테스트에는 `Target crashed`로 나온다(`dmesg`에 `Memory cgroup out of memory`).
- 수도권 1:1 도시에서는 소프트웨어 GPU로 한 프레임에 수 초가 걸린다. 페이지가 쉬지 않으니 Blink의 GC가 따라오지 못한다. 강남에서 수거 가능한 쓰레기만으로 Blink 힙이 몇 프레임 만에 0.2 → 3.4 GB로 커졌다. GC를 강제하면 0.12–0.17 GB에 머문다.
- 그래서 `GL_ARGS`에 `--js-flags=--expose-gc`를 넣었다. `freeze()`가 만드는 `window.__upd`는 5번 갱신마다 전체 GC를 부른다. 실제 GPU에서는 남는 시간에 브라우저가 스스로 GC한다.
- 화면 읽기(`shot()`)도 같은 문제였다. 화질 1의 도시 한 프레임은 소프트웨어 GPU에서 30 s 넘게 걸린다. 예전 `drawImage`/`getImageData` 읽기는 그동안 렌더러 메인 스레드를 막았다. 그 사이 렌더러의 익명 메모리가 초당 수백 MB씩 늘었다(6–8 GB까지). `light-skip-identity`는 네 번 중 두 번 종료됐다. 지금은 같은 작업 안에서 pixel-pack 버퍼로 복사하고 fence를 이벤트 루프 사이사이 기다린다. 바이트는 예전 방식과 같다(diff 0 확인). 렌더러 최고치는 3.7 GB다. 이 읽기는 페이지 안의 `window.__readFrame()`이다. 사진을 직접 찍는 테스트(`streetscape`)도 이 함수를 쓴다. 새 빌드(실제 건물 비율 0.669)에서 그 테스트도 같은 이유로 죽었다. 같은 방식으로 직접 읽는 다른 테스트(`realbuildings` 등)는 아직 통과하므로 그대로 둔다. 죽으면 같은 함수로 바꾼다.
- 원인 찾는 법: CDP `Runtime.getHeapUsage`의 `embedderHeapUsedSize`(Blink 힙)를 본다. `performance.memory`는 거칠고 갱신이 드물다. 다음으로 `Tracing.requestMemoryDump`(memory-infra)로 할당기별 크기를 본다. 메인 스레드가 막혀 있으면 CDP가 답하지 않는다. 그럴 때는 `/proc/<renderer pid>/smaps`로 익명 메모리와 공유 메모리를 나눠 보고, `Profiler`로 어디서 막히는지 본다.
- 페이지 안에서 그리는 프레임을 여러 개 쉬지 않고 이어 그리면(예전 `no-runtime-compile`의 사건 구간) 같은 이유로 렌더러가 30 s에 2 GB씩 커져 죽었다. 그린 프레임마다 `gc()`와 `setTimeout`으로 이벤트 루프에 차례를 준다(2026-11-05).
- 자동 주행 그래프(`src/worldnav.js`)는 표본마다 JS 배열을 하나씩 두다가 CSR 배열로 바뀌었다. 부팅 직후 JS 힙이 2.47 → 2.06 GB로 줄었고, 이웃 순서와 경로는 같다.

## 실행

```bash
cd build && npm i && cd ..          # 처음 한 번 (three, rapier, esbuild …)
node build/build.mjs                # 테스트는 빌드한 폴더 dist/Korea/game 을 연다 (--zip 은 전달용 zip도)
node tests/run.cjs quick            # 단위 + 부팅 + 컬링·조명 동일성 (약 5분)
node tests/run.cjs render gameplay  # 스위트 지정
node tests/run.cjs --only breach    # 테스트 하나
# 주의: 테스트의 `q` 옵션이 0이면 이제 '극단 저사양'(후처리·원경·외벽 장식 없음)이다. 화질에 의존하는 테스트는 q:1 이상을 쓴다.
node tests/run.cjs                  # 전체 (약 16분, 4코어 컨테이너 기준 · 2026-10-09 18/18 통과)
```

- Playwright: `require('playwright')`가 안 되면 `PLAYWRIGHT` 환경변수 경로(기본 `/opt/node22/lib/node_modules/playwright`)를 쓴다. 다른 빌드 폴더는 `GAME_DIR=/path/to/Korea/game`(그 안의 `index.html`). `file://`로는 열리지 않는다.
- 결과: 터미널 요약 + `tests/results/last-run.json`(git 제외).
- 테스트는 **하나씩 순서대로** 돈다. 병렬로 돌리면 시간 측정 테스트가 흔들린다.

## 기준 장면 (AAA-PLAN Q0-3, `src/views.js`)
- 열두 장면(장소, 시각, 날씨, 카메라 고정)으로 화면 변경을 전후로 비교한다. 화면이 바뀌는 PR은 전후 시트를 함께 낸다.
- 시트: `node tests/tools/golden-views.cjs`(결과 `tests/results/golden-views.png`, 커밋 안 함). `PICK=1,5`로 일부만, `TWICE=1`로 같은 장면을 두 번 찍어 바이트 차이를 출력, `Q=0..3` 화질.
- 실기기: `Korea.exe`로 연 창의 주소 끝에 `?view=3&q=3`을 붙여 열고(또는 http://127.0.0.1:47820/?view=3&q=3) 시작하면 그 장면에 카메라가 고정되고 HUD가 숨는다(사진 모드의 촬영 버튼으로 저장).
- 시작 전에 `Math.random`을 고정 시드로 바꾸고(`openGame({init})`), 땅 타일과 도시 근거리 타일이 다 들어올 때까지(최대 600프레임) 기다린다.

## 지역 확인 (WLD-21d, ADR-0036)
- `[GAME_DIR=<빌드>/game] [OUT=그림.jpg] node tests/tools/region-check.cjs <id>`: 그 시·도의 상세 도시(없으면 시청)로 가서 4초를 진행한다. 결과 한 줄에 다음을 남긴다.
  - 페이지 오류
  - 실린 월드 파일, 그 지역 파일(`<id>.pak`)이 실렸는지
  - 주변 16 m 타일 25개의 출처(그 지역 파일 / 다른 구운 파일 / 없음 = 페이지가 계산)
  - 4 km 격자 400점에서 지면 높이가 NaN인 수
  - 화면 한 장
- 합격: 오류 0, NaN 0. 지역 하나만 구운 빌드(`REGIONS=<id> node build/build.mjs`)에서 그 지역과 빠진 지역을 하나씩 확인한다.

## 새 테스트 작성 규칙
- `tests/e2e/<이름>.test.cjs`: `run(name, {q, width, height}, async ({page}) => { … result(name, pass, metrics) })`. 게임을 손으로 진행할 때는 먼저 `freeze(page)`(rAF 루프 정지, 진짜 update는 `window.__upd`).
- 픽셀 비교는 `shot(page)` + `pixelDiff`. GPU 시간은 재지 않는다. 시간 측정은 렌더를 끄고(`g.eng.render = () => {}`) 한다.
- 합격 기준은 **수치로** 결과에 남긴다(metrics). 실패 시 원인을 볼 수 있게.
- 스위트 등록: `tests/run.cjs`의 `SUITES`.
- 내부 구조 의존을 줄이는 테스트 API는 ARC-02에서 도입 예정.
